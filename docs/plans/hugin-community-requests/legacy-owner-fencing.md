# Context/JARVIS legacy owner fence and private activation evidence

## Owner decisions (supersede earlier retirement/drain plans)

- A public Context collection is public **to read**. Its Git token is a secret **write credential** with independent authority until expiry or explicit token revocation. Removing the issuer as an administrator blocks new privileged issuance/list/revoke operations; it does **not** revoke existing tokens. Current administrators explicitly revoke public tokens through Context management. Private tokens/collections are unchanged.
- Consequently, no destructive public-token retirement, orphan-repository classification, pagination migration, generation tagging or token deletion runs during activation. The installed Artifacts binding's token listing has no continuation, and historical untagged UUID repositories can lose their domain/visibility provenance on failed deletion. Those findings explain why automatic retirement could not safely be implemented; they are **not blockers under the approved independent-credential semantics**. No live tokens were accessed or changed.
- JARVIS policy `get()` is an ordinary value-only provider read. Its revision/chat/code scopes already appear in ordinary singleton authority keys; `syncCode` is nonsensitive UI metadata. Reading/modifying a returned copy conveys no write authority. Retained old ordinary accounts must keep working. Upgraded administration UI reads still check their current authorization, but owner-level read revocation is not promised. JARVIS `update()` remains privileged.
- Finance stays deployment-configured independently; all four existing admins/operators, owners/direct shares, private Context, hidden JARVIS UI, ordinary sessions and other release work are preserved.

## Implemented enforcement

Context collection owners require backend-issued current `context-public` authorization for public initialization, metadata/document mutations, manual Git sync, token issuance/list/revoke and deletion. Registry insertion/removal requires the same authorization. The immutable current UI capability forwards its authorization on every owner call. Missing authorization fails closed at the resource owner, including old boolean child wire shapes. Private owner paths never depend on administrator authority; bundled content remains immutable. Account-revocation deletion rejects public collections.

JARVIS policy owner `update(input, authorization)` requires current `jarvis-policy` authorization. Missing/wrong-purpose/revoked generations and authority outages deny. The old one-argument mutation wire shape fails; ordinary `get()` remains available. Revocation rejects admissions checked after the commit, not already-admitted operations or independent credentials.

## Private provider-first evidence

`GatekeeperVendor.adminFenceReadiness` is optional on the binding-only shared interface, implemented only by Context/JARVIS. It is not forwarded by user/account/gadget/browser APIs and is not a boolean supplied by the frontend or deployment environment.

1. Backend creates a challenge with current AdminAuthority epoch/revision and a fresh unpredictable nonce. The configured service binding, not an account wrapper, determines the provider/domain.
2. Context vendor uses its actual normalized binding `sharingDomain`. Its registry snapshots at most 1,000 currently indexed public IDs, checks every actual collection owner's identity/domain/fence version, hashes the sorted IDs and requires an unchanged registry revision after all awaited owner/hash operations. Missing/private/mismatched owners, oversize, failure and concurrent registry writes deny; no partial result counts as success. No token API is called.
3. JARVIS vendor delegates to the actual global policy owner, which attests its guarded mutation version and fixed resource identity without MCP, token or credential reads.
4. Backend validates exact provider/challenge/version and bounded fields for **both** Context and JARVIS. Missing bindings or old methods deny: absence is not proof that historical privileged accounts never existed. It then performs a second complete scan with a distinct nonce. Provider/domain/version/revision/count/inventory must match exactly across scans. No positive readiness cache exists.
5. Only after both scans does the existing authority transaction recheck current actor, expected revision, epoch and bootstrap digest, atomically writing managed mode, audit/receipt and a bounded immutable provider baseline in `authority_meta`. Failed scans/drift/concurrent activation leave no partial mode/baseline write. Old prepared records need no reset or new preparation: preparation remains unchanged; the baseline is first recorded with successful activation.
6. Subsequent AutoBuild readiness calls `AdminAuthority.assertProvidersCurrent()`: fresh complete scans must match the recorded provider/domain/fence versions and unchanged authority revision. Inventory may legitimately grow, but every current indexed owner must attest. A changed domain/version or outage restores `LEGACY_CAPABILITIES_UNDRAINED` for readiness. Image/pricing/notifier and every other gate remain untouched.

Prepared administrator UI says evidence is pending; no source/test result is live rollout approval. The blocker is cleared for activation only by this real private path, not by test success, advertised account protocol, a browser refresh or an operator-supplied flag.

## Deployment, migrations and rollback

- Keep existing Worker names, service bindings, DO classes/namespaces and Context sharing domains. No new production binding, environment variable, class migration or renumbered migration is needed. The Context registry adds a typed-storage revision singleton; existing registries start at zero and subsequent writes increment it. AdminAuthority retains schema version/history and adds its baseline only at activation.
- Within the single authorized release, deploy Context/JARVIS **resource owners first**, then consumers. Backend uses current configured vendor service bindings, not stored account wrappers, to obtain evidence. Verify exact configured binding/domain and owner-version coverage using that path before explicitly activating. Preserve backend v4/v5 and every existing provider migration tag.
- Tests exercise old wire arguments against current resource owners and actual provider entrypoint delegation. They do **not** simulate Cloudflare deployment version pinning or establish transitive native capability drain. The supported guarantee is limited to the attested resource owners; do not call an arbitrary old service/stub or namespace restart a generic drain mechanism. An operator must not route those namespaces back to unfenced code after activation.
- Before activation, rollback may preserve legacy/prepared authority, but removing provider fences reopens boolean mutation authority. After managed membership changes, do not roll back to static-only authorization, change the attested domains, delete authority/registry history or remove owner fences. Stop admissions and roll forward. Baseline migration needs a separately code-backed maintenance path; ordinary retries never overwrite it. Rollback does not revoke independent tokens, cancel already-admitted work or unsend external writes.
- No commit, push, merge, deploy, live bootstrap, provider call, token revocation or executed rollback occurred in this implementation step.

## Evidence split and type regression

The backend combined workerd harness uses typed native bridges that forward protocol arguments to the real Context registry/collection and JARVIS policy owners; they cannot synthesize a positive attestation. Full provider Worker Env types cannot be merged with the backend's augmented Env without widening shared base interfaces. Rather than do that, separate real-workerd tests exercise the actual Context and JARVIS vendor entrypoints in provider-only programs. JARVIS's native test uses the already-installed Context Vitest 4/pool tooling; its ordinary Node/Vitest 3 suite and dependencies are unchanged. Native userAgent assertions remain mandatory.

The initial immediate-rejection tests exposed the installed pool's callable-thenable queue behavior. Expected immediate owner denials are asserted inside `runInDurableObject`, returning only a bounded exact denial result; unexpected success/error fails. Other retained Context child calls still cross real native RPC, and all positive authorized paths use real owner code. No rejection filters, runtime patches or production throw-timing workaround were added. Historical failing logs remain evidence, not passing tests.

The server build regression was at consumption of native `Rpc.Result` array/promise-pipeline intersections: contextual inference lost the array callback element and generic retry result. `user.ts` already declares exact value-array return types. `server.ts` now materializes the coding-session result with `Awaited<ReturnType<UserDurableObject["listCodingSessions"]>>` and gives the async retry thunk the actual `ReturnType<UserDurableObject["listLibraryBlueprints"]>`. This converts the native result into its declared value Promise before array/generic inference; no cast, `any`, duplicated RPC interface, declaration/runtime/dependency change or behavioral retry change was made. Current explicit test-program typing and shipped builds validate the fix; this does not attribute the regression to an unrelated historical package change.
