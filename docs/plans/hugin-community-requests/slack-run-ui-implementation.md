## Delivery semantics

Key binds trusted deployment origin/run/attempt/verified PR. The backend persists each send attempt before invoking the private receiver. HTTP200 is acknowledged only for strict `ok:true`, matching channel and bounded timestamp, without a contradictory error. Only HTTP429 + parsed `ok:false` + documented rate-limit error + positive integer Retry-After (at most3600 seconds) is automatically retried. Retry waits at least the provider delay and exponential backoff; six attempts exhaust to `blocked`. Delay is never clamped downward.

All conflicting/malformed/oversized responses, redirects, 5xx, network/timeout failures and lost private RPC acknowledgements are `ambiguous`, with no automatic resend. The backend has its own fifteen-second acknowledgement deadline. A restart encountering persisted `sending` records marks them ambiguous, rather than inventing delivery or retrying. A normal acknowledgement is durable; duplicate enqueue cannot create another delivery. Changed inputs for the same run conflict.

This is **not exactly once**. Slack receives no dedupe guarantee. A crash after committing intent but before HTTP can yield an ambiguous *unsent* message; a crash after Slack accepts can yield an ambiguous *sent* message. Both deliberately require operator reconciliation. `queued`/`retry_wait`/`sending` are not `acknowledged`. Blocked/suppressed/ambiguous records have no public retry/control API or automatic reset. No receipt lookup or manual reconciliation write API is implemented; operators must not edit SQLite to manufacture success or blindly resend.
