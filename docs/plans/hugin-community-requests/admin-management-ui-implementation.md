## Behavior and safety

- Legacy/prepared modes list every backend-returned static profile ID (including all four configured production seeds), distinguish stored grants from effective static membership, and show server-owned Finance/drain blockers. Lookup is usable in transition mode; mutations remain unavailable because the backend is not managed. There is no UI bootstrap/cutover override, guessed seed removal or mocked production readiness.
- Managed-mode controls are usable against the same real API. Grant requires exact existing-account resolution and explicit confirmation of display label, exact profile ID and account ID. Regrant re-resolves the existing profile. Lookup does not trim, lowercase, rewrite aliases or create accounts. Revocation targets the exact principal from the private list, not an editable email. Self-revoke is unavailable for the known current account; the backend remains the authority for self/last-admin protection and every mutation.
- A confirmation freezes the observed authority revision and mutation key. No optimistic grant/revoke success. Success appears only after the backend returns its committed revision. A concurrent revision conflict discards the confirmation and requires refresh plus new explicit confirmation; membership pages with inconsistent revisions are discarded rather than merged.
- Unknown mutation errors are outcome-unknown, not success/failure assertions. The retry button sends the identical envelope/key; double submissions are locked. Keys live only for the open confirmation, not across tab close/reload. Closing an uncertain confirmation means refresh and inspect membership/audit before deciding again; no browser-persistent receipt store was added.
- Known self/last-admin, permission loss, pending cutover, account-not-found, already-granted/revoked and authority-unavailable errors have bounded display-safe messages. Raw thrown diagnostics are not rendered. Permission/storage failures remove private rows and disable mutations until a new successful read. Private audit is paged, oldest first, with actor/target, action, generations, timestamp and revision.
- The panel borrows the page's capability; it does not dispose somebody else's stub or put a callable stub in raw React state. The page owns disposal, including a capability arriving after unmount. Account changes hide the old capability; canceled settings and membership reads cannot update the new view. No authority is cached as a browser permission decision.
- Revocation text accurately distinguishes new admissions from already-admitted work, and explains that regrant does not revive old capabilities. Ordinary board access/static moderation and the four seeds are unchanged.

## Narrow compatibility correction

Fresh uncached frontend typing exposed a pre-existing authority-slice cross-runtime gap: `AuthorizedAppUiContext.authorization?: Service<AdminAuthorization>` referenced a Worker global absent from the frontend's existing type shim (`TS2304`). Earlier broad build results did not establish this fresh frontend check; do not treat their replayed outputs as evidence against this diagnostic.

With supervisor approval, the shared property now uses **`Fetcher<AdminAuthorization>`**. The pinned real Workers declaration defines `Service<T>` as `Fetcher<T>` for a `WorkerEntrypoint` instance, which `AdminAuthorization` extends. This is the same native service type/brand and runtime protocol, using the browser's already-existing derived `Fetcher` compatibility type. It is NOT a new mirrored interface/cast, global `any`, or a conversion to `Rpc.Stub`: the latter requires `dup`, disposal and a unique stub brand absent from service bindings. All actual issuer, backend forwarding, provider constructor assignments and the combined authority harness compile freshly without casts or signature widening. No dependency/shim/native implementation changed.
