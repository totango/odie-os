## Implemented

- Separate SQLite `AdminAuthority` singleton reached through `ctx.exports`: versioned metadata/epoch/revision, retained grant generations and provenance, private paged audit and canonical mutation receipts. Unknown/incomplete existing authority schema or missing metadata fails closed; reconstruction never resets existing managed history into static membership.
- Exact configured account checks preserve all four Odie seeds, spelling, alias/account separation and password-account compatibility. Bootstrap preview resolves every configured profile through `whoamiIfExists`; missing accounts/digest disagreement prevent preparation. One-time confirmed preparation records all resolved seeds; it does not change effective static membership or union configuration on restart.
- Real managed grant/revoke/transition transactions. Each mutation checks current actor and purpose in the synchronous transaction, then revision/idempotency payload, self/last-admin invariants, generation change, audit and receipt. Revoked actors cannot read an idempotency receipt. Regrant advances the retained generation. Transition acquires private evidence before revalidating the exact local revision at commit; no network await in SQL transactions.
- Native `AdminAuthorizationEntrypoint` references carry fixed principal/profile/purpose/mode/epoch/generation props. The service reference itself fixes the deployment/authority namespace. Its only authority method is `assertCurrent(expectedPurpose)`; consumers must supply the constant matching their purpose. There is no browser/gadget mint route, readiness override, positive KV cache or static fallback on new-path authority outage.
- Every existing `AdminApiImpl` read/write checks the issuance claim. New methods: `listAdministrators`, `resolveAdministratorCandidate`, `previewAdministratorBootstrap`, `prepareAdministratorBootstrap`, `activateManagedAdministrators`, `grantAdministrator`, `revokeAdministrator`, `listAdministratorAudit`. Mutation results are revision numbers; inputs contain no actor identity. Shared contracts and per-member documentation live in `workshop-shared/src/admin-authority.ts`, re-exported by `api.ts`.
- Board hidden reads/moderation and privileged app discovery/open use fresh authority. Ordinary signed-in public board reads do not query authority; ordinary app listing/open degrades to no admin features on authority outage rather than failing private management. Account protocol support is explicitly advertised by `AccountDescription.adminAuthorizationProtocol`, independently of `providesUi`; it is compatibility metadata, not admin or ambient authority. Context remains discoverable. **JARVIS remains hidden**, preserving its existing product contract and test, while its existing policy capability supports current checks.
- New `startAppUiAuthorized` provider path and User dispatch: missing Context/JARVIS/admin-only protocol denies; a new-path denial or outage is never retried through boolean authorization. Unrelated ordinary legacy UIs receive `isAdmin:false`, and upgraded ordinary providers receive no authorization. Only Context/JARVIS can receive purpose-limited app authorization. Context public create/write/delete/Git-backed management/editability and JARVIS policy get/update check current native authority; Context private ownership remains independent.
- Additive backend `v5-admin-authority` follows board v4 in both configs; base v3 `NativeBrowserFlow` and production empty v3 are unchanged. Existing type generator produced the backend namespace declaration with normalized source mainModule. Generic release golden/history tests and Odie provider-before-backend ordering assertions cover migration/deploy compatibility. No migration was applied live.
